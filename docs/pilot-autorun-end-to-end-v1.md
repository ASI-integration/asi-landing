# Pilot Auto-Run End-to-End v1

## Назначение и границы

`pilot-autorun-orchestrator.ts` связывает принятые внутренние модули в один безопасный конвейер для заявки, профиля объекта и операционной брони. Он не вызывает внешние API, не публикует объект или цены в OTA, не хранит доступы, не выполняет реальные legal/payment/MVD-действия и не отправляет сообщения. Коммуникации создаются только как намерения/черновики и проходят существующую policy-классификацию.

## Аудит переходов до реализации

| Переход | Состояние | Что уже было / разрыв |
|---|---|---|
| Заявка → настройка владельца | `semi_automatic` | Идемпотентная инициализация существовала, но запускалась отдельным действием. |
| Настройка владельца → профиль объекта | `manual` | Объект нельзя создавать без подтверждённого реального объекта. Следующий шаг должен оставаться явным. |
| Профиль объекта → профиль цен | `semi_automatic` | Инициализатор существовал отдельно; недостающие цены корректно оставались пустыми. |
| Профиль цен → рыночные сигналы | `semi_automatic` | Были ручные/provider-ready источники без единого запуска. Внешний поставщик отсутствует намеренно. |
| Цены → пакет публикации | `semi_automatic` | Снимок цен и пакет существовали, но не запускались одной цепочкой. |
| Профиль объекта → onboarding менеджера каналов | `semi_automatic` | Контур существовал; провайдер должен быть выбран владельцем/оператором. |
| Onboarding → готовность публикации | `semi_automatic` | Проверки существовали; реальные доступы и операторская проверка остаются ручными. |
| Входящая бронь → lifecycle | `automatic` | Intake уже создавал Booking Ops и базовые модули. Не было общего повторного запуска для существующей записи. |
| Lifecycle → legal/payment/MVD | `automatic` | Создаются только внутренние placeholders; реальные действия всегда ручные/внешние. |
| Lifecycle → заезд/проживание/выезд | `automatic` | Базовые записи и пересчёт готовы и идемпотентны. |
| Бронь → операционные задачи | `automatic` | Task sync идемпотентен при наличии объекта и дат; иначе переход `blocked`. |
| Намерения коммуникаций → auto-send policy | `automatic` | Черновики классифицируются существующей политикой. Реальная отправка этим сервисом запрещена. |
| Исключение → fallback | `semi_automatic` | Реальный блокер фиксируется в run-аудите; снятие причины остаётся ручным. |

Классы `missing` после реализации: единый run/audit-контракт, общие status/explain API и общая UI-панель были добавлены. Намеренно `blocked`: внешний API провайдера, OTA push/publishing, платёжные и государственные интеграции, глобальная автоотправка.

## Автоматизированные области

### Заявка

1. Находит существующий профиль владельца или создаёт его один раз.
2. Создаёт безопасный черновик старта настройки через существующий owner setup.
3. Не создаёт выдуманный объект. Если реального объекта нет, возвращает блокер и следующий шаг.

### Профиль объекта

1. Пересчитывает готовность и сохраняет реальные пропуски.
2. Без дублей ставит в очередь запрос недостающих данных и фотографий.
3. Идемпотентно создаёт профиль цен и профиль аудитории.
4. Создаёт только ручной источник рыночных сигналов.
5. Строит тарифную сетку лишь при корректных base/min/max и отсутствии блокеров сигналов.
6. Инициализирует onboarding только для явно выбранного провайдера.
7. Создаёт и валидирует пакет публикации, но ничего не публикует.

### Операционная бронь

1. Инициализирует lifecycle и ручные legal/payment/MVD placeholders.
2. Инициализирует заезд, проживание и выезд; пересчитывает готовность к заезду.
3. Синхронизирует задачи только при наличии объекта и обеих дат.
4. Создаёт/обновляет безопасные коммуникационные намерения и policy-решения без отправки.

## Состояние и аудит

`booking_pilot_autorun_runs` хранит итог запуска, выполненные шаги, блокеры, предупреждения, безопасное резюме и следующие действия. `booking_pilot_autorun_step_events` хранит один результат на шаг в рамках запуска. Обе таблицы закрыты для `anon` и `authenticated`; доступ имеет только серверный `service_role`.

Статусы: `queued`, `running`, `completed`, `completed_with_warnings`, `blocked`, `failed`, `dry_run`.

## Dry-run и идемпотентность

Dry-run читает текущее состояние, пишет только собственный run/step audit и не вызывает изменяющие функции модулей. Обычный запуск переиспользует существующие owner setup, pricing profile, audience, market source, channel connection, publication package, lifecycle rows, tasks и communications. Повторный запуск не означает повторную внешнюю операцию: внешних операций в сервисе нет.

## API и UI

- `POST /api/dashboard/pilot-autorun/run` — только ops admin; run/dry-run/fallback.
- `GET /api/dashboard/pilot-autorun/status` — авторизованный CRM operator.
- `GET /api/dashboard/pilot-autorun/explain` — безопасное объяснение и safety-флаги.

Панель «Автозапуск пилота» добавлена в заявки, данные объектов и Booking Ops. Основной вид показывает статус, число шагов/блокеров, следующий шаг и время. Дополнительные действия свёрнуты.

## Остаётся ручным

- выбор и подтверждение реального объекта;
- ввод недостающих данных, фотографий и ценовых ограничений;
- выбор провайдера и безопасная передача доступа;
- проверка пакета и реальная публикация;
- реальные договоры, платежи и действия МВД;
- снятие нестандартных блокеров;
- разрешение scope и отдельный запуск существующего auto-send executor.

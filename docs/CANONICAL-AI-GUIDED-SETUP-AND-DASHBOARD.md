\# ASI Canonical Blueprint\## AI-Guided Setup Doctrine + Dashboard Architecture + PMS → Objects → Master Card FlowStatus: CanonicalScope: Product logic, dashboard logic, setup logic, AI-guided interaction doctrineApplies to: landing, dashboard, onboarding, PMS connection, object setup, automation setup, future modules\---\# 1. Core Product Principle\## ASI does not give the user a form.\## ASI gives the user a guided route.The user must never be left alone in front of a large, complex, blank setup form.Every complex action in ASI must be:\- guided\- step-by-step\- AI-assisted\- reversible later\- progressively disclosedThe system must always:\- show only the next relevant step\- explain why this step matters\- offer choices instead of raw complexity\- suggest defaults when possible\- allow later edits\- prevent user dead ends\- reduce cognitive loadThis is a canonical product rule and should apply across all modules and flows.\---\# 2. Canonical UX Doctrine\## The user must not see full complexity at once.Instead of exposing many tabs, fields, and decisions at once, ASI must:\- narrow the decision space\- ask one logical question or one logical group of questions at a time\- adapt the next step based on the previous answer\- use guided setup flows instead of static forms\## Canonical interaction model:\- step-by-step guided setup\- progressive disclosure\- AI-assisted decision flow\- clear next action\- clear current step\- clear ability to change later\## Canonical rule:A user should never think:\- "What do I fill in next?"\- "Where do I click now?"\- "What is required here?"\- "What if I make a mistake?"The system must answer those questions proactively.\---\# 3. AI-Guided Setup PrincipleComplex setup in ASI must not be handled by static UI alone.It must be accompanied by the ASI communication / AI guidance layer.This means:\- setup flows should be guided by AI\- the AI should explain what is being asked\- the AI should suggest the next best step\- the AI should adapt the flow to user context\- the AI should reduce support load and avoid human-call-center dependency\## Canonical rule:AI guidance is not a separate optional widget.It is part of the setup architecture.\---\# 4. Dashboard: Canonical Main NavigationThe authenticated dashboard should use this structure:1\. Обзор2\. Источник данных3\. Объекты4\. Коммуникация5\. Бронирования6\. Автоматизация7\. НастройкиNotes:\- naming should be in Russian in RU dashboard\- dead or unfinished sections must not look fully active\- if a section is not yet functional, it should be shown honestly as limited / soon / unavailable\---\# 5. Dashboard Overview: Canonical First ScreenThe overview page should answer 4 questions:1\. What is connected?2\. What is currently working?3\. What mode am I in?4\. What is the next best step?\## Canonical blocks on Overview:\### A. Account StateMust show:\- workspace / account name\- current mode\- trial / active status\- high-level system status\### B. Data SourceMain block:\- Подключить менеджер каналов / PMS\- show connection status:&#x20; - не подключено&#x20; - в процессе&#x20; - подключено\### C. Contour StatusShow status of major contours:\- Коммуникация\- Данные / бронирования\- Автоматизация\- ПлатежиPossible statuses:\- активно\- требует настройки\- скоро\### D. Next Best ActionOnly one clear next action block, such as:\- подключить PMS\- завершить настройку\- запросить подключение другой системы\- выбрать режим работы\## Must NOT be on overview:\- fake recent activity\- fake working controls\- large dead placeholder blocks\- communication-channel setup as the primary connection block\- manual location calculation as the main dashboard function\---\# 6. Data Source Logic: Canonical RuleThe main data connection concept is NOT:\- communication channels\- individual OTA platforms one by oneThe correct model is:\## Connect PMS / Channel Manager as the main source of booking and availability data.Canonical options may include:\- RealtyCalendar\- Bnovo\- TravelLine\- Другая системаThese items should be shown as:\- honest list options\- large readable selection items\- not tiny pills\- not fake active buttons if not yet connected\## Canonical note:The system should use PMS / channel manager as the main source for:\- reservations\- availability\- pricing\- property mapping\- operational data ingestion\---\# 7. Object Setup Logic: Canonical RuleThe user must not repeatedly enter the same property information across many systems manually.ASI must be built around:\## a canonical Master Card of the property.The Master Card is the structured internal source of truth for each object.It should include:\- property type\- title\- address\- description\- photos\- amenities\- rules\- check-in/out\- beds / bathrooms / capacity\- floor / elevator / parking / balcony / etc.\- operational metadata\---\# 8. PMS → Objects → Master Card FlowThis is the canonical setup flow for onboarding inventory.\## Step 1. Connect PMS / Channel ManagerThe user selects their system and connects the source.\## Step 2. Import ObjectsASI pulls available object data from the connected system.\## Step 3. Assess Data CompletenessASI evaluates what is already present and what is missing.\## Step 4. Guided CompletionThe user is guided only through the missing fields and unresolved decisions.\## Step 5. Template LogicIf objects are similar, ASI should support templates by:\- company\- object type\- portfolio group\## Step 6. Bulk ApplyTemplates and common defaults should be applied to many objects at once.\## Step 7. Master Card FinalizationEach object ends with a canonical internal profile.\## Step 8. ReadinessASI shows readiness status for downstream contours.\---\# 9. Canonical Rule for Large PortfoliosASI must not assume one-object-at-a-time manual setup.The system should support:\- template-based setup\- grouped setup by object type\- bulk actions\- missing-field completion\- portfolio-scale workflowsThis is essential not only for:\- 25 objects\- 50 objectsbut also for:\- 100+\- 600+\## Canonical rule:For larger portfolios, the system should ask:\- Are most objects similar?\- Are there several object types?\- Are objects mostly unique?Based on that, the system should choose:\- one template\- multiple templates\- or import-first / fill-missing-only mode\---\# 10. Location Module: Canonical PositionThe location module is important, but in the dashboard it should NOT be treated as the user's primary day-to-day operational interface.Its canonical roles are:\- demonstration\- diagnostics\- manual analysis mode\- onboarding support\- strategy review supportIn normal automated operation, the system should use location intelligence internally without forcing the user to manually run it all the time.\## Canonical rule:Location analysis is a system intelligence layer first, and a manual interface second.\---\# 11. Communication Module: Canonical PositionThe communication module is not just a messaging feature.It is also part of:\- user guidance\- AI-assisted setup\- support load reduction\- next-step orchestration\## Canonical rule:The communication module and guided setup logic should work together.This means:\- AI should guide the user through setup\- AI should answer setup questions\- AI should reduce the need for human support\- AI should help the user continue from the current step\---\# 12. Third Foundational ModuleASI should not present only two foundational modules long-term.For the first meaningful foundation, there should be three:1\. Коммуникация2\. Оценка локации3\. Бронирования и размещениеAlternative naming allowed if product language improves later, but the role is:\## The third foundational module handles booking / placement / intake / operational booking contourThis may eventually include:\- reservation intake\- data distribution\- booking flow support\- operational placement logic\- later operational expansion\---\# 13. Canonical Setup UI PatternComplex setup should be implemented as:\- guided step flow\- wizard-like interaction\- sliding / progressive steps\- one logical step at a timeThe UI should not dump large multi-section forms at once.Instead:\- user answers a structured step\- next step appears\- flow adapts based on answer\- user always knows what comes next\## Canonical rule:ASI setup should feel like being guided, not like filling enterprise paperwork.\---\# 14. Text and Visual Readability RuleAcross ASI:\- headings should be larger\- body text should be noticeably larger than typical cramped SaaS defaults\- critical selections must be large and readable\- important lists should not be tiny pills if they represent meaningful choicesIf an element is not clickable, it must not look like a button.If an element is important to choose from, it should be large and readable.\---\# 15. Truthfulness RuleIf a function is not fully working yet:\- do not present it as active\- do not use fake activity\- do not imply fake completeness\- prefer honest placeholders over misleading controlsCanonical treatments:\- скоро\- недоступно\- по запросу\- требует настройкиA smaller honest dashboard is better than a larger fake-complete dashboard.\---\# 16. Immediate Product DirectionCurrent product direction should prioritize:1\. Honest dashboard2\. PMS / channel manager connection logic3\. Guided import of objects4\. Master Card architecture5\. AI-guided setup experience6\. Communication + setup guidance integration7\. Operational booking / placement contour definition\---\# 17. Canonical SummaryASI is not a pile of forms and modules.ASI is a guided operational system.Its canonical setup philosophy is:\- connect one source of truth\- import existing data\- complete only what is missing\- guide the user through each step\- let AI reduce complexity continuously\- scale from one object to large portfolios\- keep every unfinished area honestThis document is canonical and should be used by all future implementation agents, design passes, dashboard refactors, and onboarding architecture work.

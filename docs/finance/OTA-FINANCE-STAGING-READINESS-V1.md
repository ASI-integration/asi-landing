# OTA finance: PostgreSQL session gate and denied-access audit (source-only)

Status: **PROPOSED — NOT INSTALLED / NOT ENABLED**. This is a stacked follow-up to draft PR #661, not a live OTA/banking feature.

## Changes prepared

- `src/lib/ota-finance/pg-preflight.ts` accepts an **injected server-side pool** and verifies actual connected PostgreSQL database name, current role (`service_role`), PostgreSQL >=17, schema USAGE and exact SELECT/INSERT-only grants + RLS on six private tables. For staging, the connected role must be a separately provisioned **LOGIN** role named `asi_finance_runtime`; `service_role` is explicitly rejected. Any mismatch fails closed, releasing the client. No database connection URL, TLS options, secrets, application routes or real deployment are introduced.
- `assessFinanceStagingReadiness` performs metadata SELECTs then **always releases the client**. It cannot produce an import connection.
- `guardedDisposableFinancePool` wraps an injected pool for **disposable database writes only** and refuses `staging_readiness_only` mode. In particular, importing a verified staging connection through this wrapper is blocked.
- `src/lib/ota-finance/denial-audit.ts` defines `requireAuditedOtaFinanceScope`, an opt-in future server boundary. It runs the iron-session gate, then inserts a denied decision into a caller-injected writer before rethrowing the refusal. If that insert fails, it returns a generic, fail-closed `FINANCE_DENIAL_AUDIT_UNAVAILABLE`. Successful access must not insert a denial.
- `supabase/migrations/20261116160025_ota_finance_denial_audit_v1.sql`, generated by Supabase CLI `migration new`, defines the sixth RLS-protected table, `ota_finance_private.access_denials`. It contains only a random request UUID, constrained action/reason, a SHA-256 fingerprint salted with the one-time request UUID, fixed `DENIED` outcome and timestamp. There is **no raw account, property, booking, guest, IP, session or token**. Service role can SELECT/INSERT, not UPDATE/DELETE.
- SQL and Vitest tests cover successful access with no denial, owner rejection, audit outage, missing audit confirmation, unknown action, expected database/role/PG version, table/privilege drift, connection release, staging read-only mode and disposable connection handoff.

## Staging acceptance sequence — not yet executed

1. Review and merge both dependent PRs through normal protected checks. Approve the **exact final SHA** if governance requires it; previous owner attestations do not automatically carry to changed commits.
2. Before any migration, independently verify staging target project ID, database name, current role, intended environment, maintenance window, backups, and rollback plan. Never reuse production secrets for tests.
3. Apply both approved, ordered migrations through the authorized release process **only to separately identified staging** (the current Supabase connection is not authorized here). Verify six private tables, RLS, immutable grants, FKs, and restricted API exposure. Do not grant anon/authenticated access.
4. Provision a dedicated `asi_finance_runtime` **LOGIN** role with narrowly scoped SQL privileges and reviewed RLS policies. This account does **not** exist or receive privileges as part of this PR; Supabase `service_role` is `NOLOGIN` and therefore cannot be the direct staging PostgreSQL identity. Establish an independently approved secret, least-privilege grants for the six private tables and read-only checks on identity/booking source tables, and confirm effective policies before attempting the preflight. Do not grant raw public API access.
5. Configure a trusted server runtime pool with verified TLS certificates/hostnames, secret rotation, a dedicated allowlisted network path, narrowly scoped connection limits and no `NEXT_PUBLIC_` secret. **This implementation deliberately does not instantiate that pool**. The server itself must enforce TLS validation; SQL metadata checks cannot prove client-side certificate validation.
6. Run metadata-only `assessFinanceStagingReadiness`. Treat a missing schema, wrong role or unexpected privilege as a **hard failure**. The current staging probe **does not authorize writes**; it closes the connection.
7. Perform synthetic writes and forced rollback/duplicate/unknown-COMMIT tests in a dedicated **disposable PostgreSQL 17** instance. Test denial-audit failures with injection. Do not use real payment credentials, OTA imports or banking data.
8. Before a staging write endpoint is ever enabled, separately review a server-only connection holder, access-denial wrapper wiring for every entry point, rate limiting, logging of unknown runtime failures, revocation consistency, durable audit retention, incident response and post-deployment smoke tests. A later distinct owner-authorized release must remove the deliberate staging write block.

## Explicit limitations

- The current `transactional-import.ts` and `private-reader.ts` from #661 are **not wired** to the new audit wrapper. Until endpoints are designed and verified, there is no complete persistent denial coverage.
- No real PostgreSQL driver/pool was constructed and no staging or production database was contacted, modified or migrated as part of this proposal.
- A denied request may have no trustworthy actor or tenant ID, so the audit table proves only that a scoped denial record was inserted, **not** the identity of the caller.
- Operator-normalized CSV money remains `UNVERIFIED_OPERATOR_IMPORT`, never bank-settled.
- A GitHub PASS does not establish a live G2–G6 acceptance or production readiness.

## Live metadata evidence and blocking role prerequisite

On 2026-11-16, a read-only catalog query against the connected Supabase project reported `service_role.rolcanlogin = false` and `postgres.rolcanlogin = true`. `postgres` is far broader than the future finance runtime and must not be accepted as a substitute. Consequently the staging preflight explicitly rejects `service_role`, even if a test fixture permits temporary `SET ROLE service_role`. The dedicated role, its grants and its verified secret require a separate approval; until then, **staging readiness correctly fails closed**. Do not claim staging access or a live adapter is enabled.

# Framework готовности модулей (~90%, decision-grade)

Документ задаёт **единые критерии** оценки готовности любого модуля платформы. Процент — не «ощущение полноты UI», а приближение к **production-like / decision-grade** качеству в рамках текущих данных и архитектуры.

## Разделение слоёв (обязательно)

Оценка ведётся **раздельно** для каждого слоя одного продукта:

| Слой | Смысл |
|------|--------|
| **Demo layer** | Демонстрация ценности, детерминированные или упрощённые данные, допустимы «красивые» прокси. |
| **Standalone / sellable layer** | То, что можно продавать как отдельный артефакт (отчёт, API, интеграция) с явными ограничениями и поддержкой. |
| **Core engine layer** | Исполняемая логика скоринга/решений/политик: воспроизводимость, валидация, контракты входа-выхода. |

**Нельзя** смешивать: например, «готовность демо-страницы отчёта» ≠ готовность гравитационного движка.

## Измеримые оси готовности

### 1. Logic completeness (полнота логики)

- Все ветки доменной модели, которые влияют на решение, **явно обработаны** (включая «нет данных», «конфликт сигналов», «низкая уверенность»).
- Нет скрытых «магических» констант без смысла в домене или без привязки к конфигу/документации ограничений.

### 2. Validation coverage (покрытие валидацией)

- Есть **фиксированный control set** (золотой набор кейсов) + автоматический прогон.
- Регрессии определены: что ломает релиз, что — допустимое улучшение при сохранении инвариантов.

### 3. Explainability (объяснимость)

- Для ключевого вывода есть **структурированная причина** (drivers, reasons, tier), а не только итоговая метка.
- Пользователь или аудитор видит, **какие входы** повлияли и где сигнал слабый.

### 4. UI / report completeness (полнота отчёта/интерфейса)

- Отображаются **и** итог, **и** ограничения, **и** уверенность/дисклеймеры там, где данные прокси.
- Нет «тихого» скрытия отсутствующих полей без маркировки.

### 5. Operational reliability (эксплуатационная надёжность)

- Таймауты, идемпотентность там, где есть внешние вызовы; деградация при сбое провайдера.
- Наблюдаемость: аудит, корреляция, понятные ошибки.

### 6. Integration readiness (готовность к интеграции)

- Стабильные контракты (типы, версии схем), миграции, обратная совместимость или явный breaking policy.
- Документированные точки расширения (провайдеры данных, политики).

### 7. Confidence / uncertainty handling (уверенность и неопределённость)

- Явные уровни уверенности или диапазоны; **не выдаём решение как жёсткий факт** при proxy-данных.
- Политика: когда эскалация к человеку / второй источник / «unknown».

### 8. Documented limitations (зафиксированные ограничения)

- Публичный список: ceiling данных, географии, частоты обновления, известных bias модели.

## Шкала: 60% / 75% / 90%

### ~60% — «рабочий прототип + ручная уверенность»

- Основной happy-path работает; edge cases частично.
- Валидация: разрозненные тесты или ручные прогоны без жёсткого control set.
- Объяснимость: частичная; часть выводов эвристична.
- Операционка: базовые try/catch, без полной матрицы деградации.
- **Demo layer** может выглядеть почти «готовым» при **сыром core**.

### ~75% — «пилот с дисциплиной»

- Control set существует и гоняется **регулярно** (хотя бы локально/в CI на подмножестве).
- Ограничения и proxy-данные **явно подписаны** в продукте и в коде (комментарии/типы `unknown` tier).
- Интеграции: основные адаптеры стабильны; известные провалы провайдера не роняют систему без сообщения.
- Standalone может продаваться **как pilot** с честным scope.

### ~90% — «decision-grade в рамках текущего data stack»

- Логика: доменные ветки закрыты; отсутствие данных — **первоклассный** сценарий с эффектом на скор/вердикт.
- Валидация: control set + регрессионные инварианты; принятие pass/fail после тюнинга **формализовано**.
- Explainability: структурированные причины согласованы с тем, что видит пользователь.
- Ops: SLO-minded поведение (таймауты, ретраи с backoff где уместно, идемпотентность).
- Интеграция: версионирование отчёта/API; миграции или явные breaking notes.
- Uncertainty: политика не смешивает «модель уверена» и «данных нет».
- Ограничения: отдельный раздел «что модуль **не** обещает».

### Что **не** считается 90%, даже если «фича работает»

- Красивый UI без соответствия core-логике и без валидации.
- «Работает на демо-адресах» без географически и сценарно разнообразного control set.
- Скрытая подмена реальных данных синтетикой (`report/generator`-стиль) без маркировки в sellable-слое.
- Отсутствие политики при сбое внешнего провайдера (OSM, геокодер, платёжка).
- Отсутствие аудита/трейсинга для автономных действий с деньгами или доступом.
- Один общий процент платформы без декомпозиции по модулям и слоям.

## Использование framework в roadmap

Любой workstream в roadmap обязан иметь:

1. Затронутые оси из списка выше.
2. Измеримые **acceptance criteria** (не «улучшить», а «инвариант X не ломается», «поле Y всегда заполнено или `unknown`»).
3. Указание слоя: Demo / Standalone / Core.

# Channel Manager Access & Import v1

Дата аудита: 2026-07-01.

## Граница версии

Версия создаёт безопасный внутренний слой доступа, ручного импорта и сверки. Она **не публикует** объекты, цены или доступность в OTA и не выполняет реальные вызовы Bnovo, RealtyCalendar или TravelLine. Единственный рабочий источник данных v1 — проверяемый ручной JSON-снимок. Название провайдера можно сохранить для будущего адаптера, но это не означает наличие интеграции.

Пароли, логины, API-ключи, токены и заголовки авторизации запрещены во входных данных. В `safe_access_ref` хранится только ссылка вида `vault:...`, `credential:...` или операторская отметка; API возвращает только признак её наличия.

| Статусы `ready_for_channel_preparation`, `manual_channel_publication_pending`, `channel_access_received`, `object_data_ready`, `publication_blocked` | Вычислялись owner/object setup | Сохранены; import readiness добавлен рядом | Уже автоматизировано |

Предыдущий `Distribution Runtime Phase 1` содержит техническую foundation-схему `dist_*`, mappings, snapshots и audit primitives. Она не является доказательством рабочего provider API. Access & Import v1 не пишет в неё автоматически: это исключает случайную публикацию и оставляет явную точку handoff для будущего Publishing v1.

## Модель данных

- `booking_channel_manager_connections` — провайдер, состояние подключения и доступа, только безопасная ссылка на секрет.
- `booking_channel_import_runs` — запуск, тип, счётчики, предупреждения и безопасный итог.
- `booking_channel_imported_objects` — внешний объект и результат сопоставления.
- `booking_channel_imported_bookings` — внешняя бронь и связь с Booking Ops.
- `booking_channel_calendar_snapshots` — доступность, минимальный срок и цена на дату. Строки раздела `pricing` сохраняются здесь с пометкой `snapshot_kind=pricing`.

Все таблицы имеют RLS. Прямой доступ `anon` и `authenticated` отозван; dashboard API работает серверным service role.

## Ручной снимок

```json
{
  "objects": [],
  "bookings": [],
  "calendar": [],
  "pricing": []
}
```

Ограничения: не более 1 МБ и 500 строк на раздел. Рекурсивная проверка отклоняет секретные ключи и значения. Повторный импорт обновляет строку по `(connection_id, external_id)`; календарь — по `(connection_id, external_object_id, date)`.

## Сверка

Объект:

1. Явный `property_setup_id` даёт точное сопоставление только с существующим профилем.
2. Название + город + вместимость дают точное сопоставление.
3. Только название + город дают `possible_match` и требуют оператора.
4. Низкая уверенность остаётся `unmatched`.

Бронь:

1. Внешний ID сверяется с `booking_ops_records.booking_id`.
2. Совпадающие даты без внешнего ID-сопоставления отмечаются как возможный дубликат.
3. Создание выполняется через `processInboundBookingRequest(..., 'channel_manager_placeholder')`.
4. Повторное действие возвращает существующую бронь и не создаёт дубликат.

Конфликты v1: объект не сопоставлен, возможный дубль брони, бронь есть в импорте, но не в ASI, отсутствует цена, в снимке нет объектов. Цена из снимка не перезаписывает источник цены ASI.

## Коммуникации

Создаются только draft intents в `booking_owner_setup_communication_intents`:

- `request_channel_manager_access`;
- `channel_access_received_acknowledgement`;
- `channel_import_completed_notice`;
- `channel_import_needs_review_notice`;
- `internal_status_notice`.

Каждый intent проходит существующую auto-send policy. Глобальная автоотправка не включается. Секреты и инструкции с паролями отклоняются до постановки intent; реальные сообщения этой версией не отправляются.

## API и UI

Защищённые API находятся под `/api/dashboard/channel-manager/*`; чтение требует CRM operator, изменения — Ops admin. Неавторизованный запрос получает `401`. Ответы списков не содержат `raw_snapshot`, контактную ссылку гостя, metadata подключения или значение `safe_access_ref`.

Компактная панель «МК / OTA импорт» добавлена в `/dashboard/property-knowledge` и `/dashboard/booking-ops`. Основная часть показывает статус и счётчики; JSON и редкие действия скрыты в раскрываемом блоке.

## Handoff в Publishing v1

Publishing v1 может начинаться только после отдельного подключения реального адаптера, проверки партнёрских credentials, sandbox/contract условий и явного разрешения на outbound. `import_ready` означает готовность **импортированных данных к внутренней проверке**, а не готовность или факт OTA-публикации.

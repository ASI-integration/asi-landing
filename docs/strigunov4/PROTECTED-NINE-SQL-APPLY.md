# Стригунов 4 — защищённое применение ровно девяти миграций

**Статус:** кандидат исходного кода. Не является разрешением на применение SQL и не означает, что staging уже обновлён.

## Внешние обязательные разрешения

Рабочий запуск возможен **только** после включения этого кода через штатный PR в защищённую `main`, успешных независимых проверок и отдельного ручного запуска `strigunov4-staging-sql-apply.yml` с текущим 40-символьным SHA ветки `main` и точным подтверждением `APPLY_STRIGUNOV4_NINE_SQL_<sha>`. Сценарий использует защищённое окружение GitHub `staging`: разрешена только ветка `main`, требуется одобрение назначенного проверяющего. Данные `GITHUB_*` в произвольной среде и локальные отчёты не доказывают полномочий.

**Не запускать SQL напрямую с ноутбука, по SSH на сервере, через Supabase-коннектор другого проекта либо через `supabase db push`.** Этот код ещё должен пройти отдельное независимое рассмотрение, включая правила доступа к базе. Не отключать обязательные проверки.

- Только PostgreSQL 17 staging Supabase-проекта `meeravcldnmocjtlqoeu`. Проверить адрес подключения, пользователя проекта, удостоверенный TLS (`verify-full`) и точную ветку исходного кода.
- Исходные девять файлов должны байт-в-байт совпасть с закреплёнными SHA256; собранный SQL — ровно **55 091 байт**, SHA256 `ba963872a534fb1a6852f427372ff81e498e115b92f8a98e899ba2f482e5b959`.
- Перед подключением к базе подтвердить, что у старого staging-процесса **все семь** запретов внешних отправок действительно действуют, старый выпуск `5c91b27bcde395f01cc078d1fbe454dd7436e1c6` и резервный выпуск G0 на сервере имеют проверенную идентичность.
- Шифрованная резервная копия, переданная владельцем после одобрения GitHub: запуск `39023529319`, SHA256 `e72aea476efabd3625566759748d6d819c4cea22f12ee0ec483948b41dc5afef`, 339 054 байта, закрытая папка. Её независимое восстановление на изолированной безсетевой PostgreSQL 17, сверка данных, ролей, ACL, RLS, четырёх последовательностей и девяти миграций с ROLLBACK уже прошли. Ключи внешнего хранилища и исходные пароли этим тестом не восстанавливались.
- Read-only предзапрос живой базы должен подтвердить `postgres|17|90|7|0`: ровно 90 исторических записей, все семь особых записей staging сохранены, ни одна из девяти выбранных миграций ещё не зарегистрирована. Любое расхождение блокирует запись.
- Применить единственный закреплённый SQL-пакет с одной внешней транзакцией, проверками схемы/безопасности и регистрацией только девяти миграций. После выполнения read-only история должна стать `postgres|17|99|7|9`. Не добавлять остальные миграции репозитория и не изменять чужие проекты.
- Этот пакет **не переключает приложение**, не изменяет конфигурацию сервера, не разрешает реальные email/Telegram/WhatsApp/OTA/платежи и не затрагивает Production либо Sentinel.

## Ошибки и восстановление

Отказ до SQL подтверждается как `BLOCK`. Если во время транзакции произошёл сбой, клиент не знает точно, завершился ли COMMIT: выводить **`SQL_APPLY_RESULT_UNKNOWN_OR_REJECTED`**, повторный запуск без новой сверки истории запрещён. Если после COMMIT история не соответствует ожидаемой, выводить **`POST_APPLY_HISTORY_REQUIRES_REVIEW`**. **Откат смены ссылки приложения не откатывает базу.**

Сохранённая зашифрованная копия доказывает техническую способность к восстановлению в изоляции, но восстановление рабочей базы может уничтожить появившиеся после снимка данные. Не запускать восстановление staging автоматически без отдельного анализа и разрешения владельца. Никакие пароли, приватные ключи, полный URL базы и SQL-вывод с чувствительными значениями не должны выводиться в публичные журналы.

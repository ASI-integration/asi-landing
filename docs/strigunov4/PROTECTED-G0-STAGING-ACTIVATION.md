# «Стригунов 4» — защищённая установка G0 на staging

**Текущий статус:** только исходный код и независимая приёмка. Ни один файл из данного PR не устанавливает пилот до отдельного разрешения владельца в защищённом окружении GitHub `staging`.

## Допуск к установке

1. Ветка `main` должна быть защищена; запускающий — подтверждённая учётная запись владельца `ASI-integration` (ID 207600140), только первый запуск, точный актуальный 40-символьный SHA. Для ручного запуска требуется подтверждение `ACTIVATE_STRIGUNOV4_G0_<SHA>`. Окружение `staging` имеет разрешённую ветку только `main` и обязательное одобрение назначенного владельца.
2. Из защищённых GitHub-секретов берутся **только staging**: `STAGING_DATABASE_URL` проекта `meeravcldnmocjtlqoeu`, ключ SSH, адрес/порт staging и ссылка проекта. TLS PostgreSQL проверяется `verify-full` с закреплённым CA; PostgreSQL 17 запускается через исходный закреплённый контейнер клиента. Чтение базы подтверждает `postgres|17|99|7|9`: 99 исторических записей всего, все семь staging-only сохранены, все девять миграций реально зарегистрированы.
3. Через SSH с независимо закреплённым fingerprint Ed25519 и `GlobalKnownHostsFile=none` проверяется **та же** исходная зашифрованная резервная копия 39023529319, SHA-256 `e72aea476efabd3625566759748d6d819c4cea22f12ee0ec483948b41dc5afef`. Этот архив восстановлен в изолированной лаборатории, но не означает разрешение откатывать живую базу.
4. Старое приложение должно отвечать на localhost:3001, показывать выпуск `5c91b27bcde395f01cc078d1fbe454dd7436e1c6`, иметь точную проверенную службу `asi-landing-staging` с пользователем `asi-runtime`, и **все семь** флагов запрета отправок должны реально присутствовать в `/proc/<MainPID>/environ`.

## Активация и контроль

После проверки целостности установщик атомарно переключает ссылку `/var/www/asi-staging/current` на G0 и перезапускает **только** `asi-landing-staging`. Новый процесс должен отвечать на `/api/version` своим SHA, `/api/health` — успешно, слушать `127.0.0.1:3001`, и сохранять все семь запретов реальных email, Telegram, платежей и синтетических внешних отправок. Состояние сохраняется в закрытый корневой журнал, один запуск на ID GitHub, с неблокируемым межпроцессным замком против повторных запусков.

Если активация новой версии или её фактическая проверка не проходит, выполняется попытка атомарно восстановить старую ссылку, перезапустить старую службу и подтвердить её доступность. При неудаче восстановления статус **MANUAL_RECOVERY**, не объявлять пилот готовым. Откат приложения **не откатывает БД**.

**Этот код не выполняет SQL, не меняет историю миграций, не направляет сообщения гостям и не запускает платежи.** Наличие флагов запрета отправок ещё не является доказательством нулевых внешних эффектов в полном физическом тесте. Для окончательной демонстрации нужен отдельный защищённый синтетический цикл бронирования и проверка фактической доставки/платежей с отрицательным результатом.

## Ограничение Production и Sentinel

У репозитория есть проект Vercel `asi-landing-new`, который автоматически публикует каждый коммит `main` в production. Поэтому **данный PR нельзя объединять в main до отдельно согласованной безопасной изоляции автоматического Vercel production-развёртывания**. Простое объединение кода способно косвенно затронуть Production, даже если устанавливаемый серверный сценарий касается только staging. Sentinel не используется.

# Стригунов 4 — подготовленный защищённый механизм экспорта staging

Этот пакет — реализация и кодовая приёмка **первой половины** процедуры резервирования. Не утверждать, что полное восстановление уже доказано.

## Предназначение
- Только Supabase staging meeravcldnmocjtlqoeu, PostgreSQL 17, из существующего GitHub environment staging с required reviewer и main-only.
- Отдельный workflow `.github/workflows/strigunov4-staging-secure-backup.yml` имеет только ручной запуск по точному SHA после code review/owner approval. Он не входит в deploy workflow и никогда не переключает версии, не запускает SQL-миграции и не трогает production.
- Экспорт: весь доступный logical custom PGDMP с ownership/ACL (без `--no-owner` и `--no-acl`) и отдельный `pg_dumpall --globals-only`. Дамп и роли временно существуют только в каталоге runner с правами 0700; никакие данные, пароли и полный SQL не публикуются. В лог идут только безопасные статусы, SHA256 шифртекста и размер.
- Сертификат получателя — прежний локальный RSA-3072 публичный сертификат, с фиксированным SHA256 fingerprint. Приватный ключ остаётся только у владельца на ноутбуке. CMS AES-256 шифрует пакет перед передачей.
- Долговременная шифрованная копия на отдельном от Supabase staging SSH VPS: строго `$HOME/.strigunov4-staging-backups`, права 0700 каталога и 0600 файла, sha256 проверяется до атомарного переноса. Никаких изменений `/var/www/asi`, `/var/www/asi-staging`, портов, системных unit или чужих каталогов.
- Изменения VPS не выполняются, если публичный ssh-ed25519 ключ не совпадает с известным отпечатком действующего серверного SSH, ранее подтверждённого с ноутбука через Tailscale.

## Что ещё обязательно
1. Workflow подготовлен в отдельном PR от main и не может быть запущен через защищённый main-only environment, пока изменения не пройдут независимый review и штатный контролируемый merge в main. Не обходить это условие.
2. Успех экспорта означает ТОЛЬКО COPY_RECORDED, а не RESTORE_PASS. Проверить сохранённый шифртекст на хосте и независимо скачать зашифрованную копию на ноутбук, вне той же отказной зоны.
3. На отдельном совместимом с Supabase окружении проверить дешифрование ключом владельца, восстановление ролей и всех доступных схем, владельцев, ACL, RLS, default grants, extension supabase_vault, миграционной истории, затем негативные тесты доступа. Supabase-managed системные роли/расширения требуют специального способа. На обычный Docker Postgres restore мог бы не пройти, что НЕ превращается в PASS.
4. Убедиться, что backup учитывает ограничения Supabase-hosted Storage/внешние объекты: логический PostgreSQL dump не является backup внешних файлов в object storage.
5. До RESTORE_PASS + независимого подтверждения минимального SQL — никакого staging DDL, переключения systemd, применения 49 миграций или установки G0.

## Встроенные защиты
- точный repo/main/путь workflow/staging project ref, отсутствие libpq overrides, строгий verify-full с уже закреплённым CA Supabase;
- закреплённый PostgreSQL17 Docker client, read-only PGOPTIONS; TLS сертификат сервера/hostname проверяется libpq;
- строгая SSH host key fingerprint, никаких `accept-new`, приватный ключ SSH удаляется вместе с временным каталогом;
- не записываются секреты в GitHub-логи или Actions artifact; вручную заданный подтверждающий текст и reviewed SHA.

## Замечания независимого review и пределы восстановления

Экспорт globals использует `--no-role-passwords`: роли, memberships и атрибуты сохраняются через pg_roles, без чтения закрытого pg_authid. Хэши паролей ролей в globals.sql НЕ включаются. До RESTORE_PASS обязателен отдельно подтверждённый закрытый источник credentials для каждой необходимой LOGIN-роли и фактический успешный вход после восстановления. Управляемые роли восстанавливаются совместимым способом провайдера; нельзя слепо проигрывать globals поверх managed instance или объявлять допустимыми произвольные ошибки. Нет credentials — BLOCK, а не урезанный PASS.

Vault требует проверки реального дешифрования после восстановления и доступа к совместимому encryption root key через разрешённую процедуру провайдера. Отсутствие необходимых ключей или failure decrypt — BLOCK. Offline preflight требует login_credentials_verified и vault_decryption_verified; значения должны опираться на независимые реальные доказательства, не на факт экспорта. При отсутствии Vault данных нужен документированный N/A по исходному каталогу, не молчаливый пропуск.

Docker image pull вынесен отдельно (240 сек); экспорт получает 900 сек, прочие операции сохраняют стандартный timeout. Job остаётся ограничен 25 минутами. Ошибка по-прежнему закрывает дальнейший путь.

Источники: https://www.postgresql.org/docs/17/app-pg-dumpall.html (no-role-passwords); https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore (managed restore, custom LOGIN credentials, Vault/root key). Реальная совместимость live экспорта ещё NOT_RUN.

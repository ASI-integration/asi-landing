# ASI: проверяемый выпуск «Стригунов 4»

## Зачем

Цель разработки — не бесконечное улучшение кода, а owner-accepted `READY_FOR_DEMO` на физическом staging. Состав выпуска замораживается при отдельно разрешённом объединении исходного PR этого пакета с защищённой `main`.

Единственная утверждаемая карта: [`releases/strigunov4-demo.json`](releases/strigunov4-demo.json). Она связывает шесть последовательных этапов с обязательными результатами, существующими исходниками и границами выпуска. Реальные пути, ещё не вошедшие в main, подтверждены точными HEAD открытых PR #502 и #509. Для S4-G1 отдельно закреплены три ещё не существующих плановых файла защищённого ремонта: `plannedFiles` — точные пути, не произвольные маски. Это предотвращает ситуацию, когда сама карта запрещает выполнить нужное исправление. Эта карта — начальная ограниченная карта демонстрации, а не полный каталог всех транзитивных зависимостей ASI.

## Рабочая команда

```powershell
node scripts/agent-os/check-demo-release.mjs
node --test scripts/agent-os/__tests__/demo-release.test.mjs
```

Перед началом задачи выбрать `nextStage` и конкретный критерий этого этапа. В заголовке или в теле любого нового PR после запуска политики обязательно указать строки:

```text
Release-Stage: S4-G1
Release-Mode: implementation
```

Допустимые `Release-Mode`: `implementation`, `diagnostic`, `acceptance`. Для диагностики добавить `Release-Diagnostic-Iteration: 1` или `2`. CI учитывает все предыдущие диагностические PR того же этапа из GitHub, включая открытые и закрытые без merge; последовательность сбрасывает только объединённый PR implementation или acceptance. Он запрещает повторную «первую» попытку и третью диагностику. Владелец тогда выбирает конкретный ремонт, изоляцию, ограничение объёма или точечную инженерную помощь. Исторические PR могут изменять свои описания, поэтому машинный счёт — полезный контроль, но не криптографический журнал неизменяемых решений.

## Как действует ограничение

1. Код сравнивает фактические файлы `base SHA...head SHA` (от общей базы) с закреплённым списком разрешённых путей текущего этапа. Переименование учитывает оба пути: удалённый исходный и добавленный конечный.
2. Если путь лишний, этап пропущен или изменён сам управляющий контракт, CI блокирует PR.
3. Изменить область выпуска разрешено только по **новому явному решению владельца**. Для допуска к выпуску владелец лично оставляет в PR комментарий из единственной строки (обычным изолированным проверкам кода такое разрешение не требуется):

```text
ASI-OWNER-APPROVE:RELEASE-EXCEPTION:<номер_PR>:<40-символьный_HEAD_SHA>
```

При изменении самого канона вместо `RELEASE-EXCEPTION` используется `CONTRACT-CHANGE`. Скрипт проверяет ID GitHub владельца `207600140`, точный SHA и действие по API. Обычное «approved» в тексте PR не даёт права на исключение. От имени владельца никто не должен создавать комментарий без его явного решения.

**Предел защиты от обхода ИИ:** GitHub подтверждает личность аккаунта, но не отличает владельца от ИИ, которому предоставлены права записи от имени того же аккаунта. Поэтому GitHub-комментарий от `ASI-integration` сам по себе **не является независимым человеческим разрешением**. Для изменений управляющего канона максимальная защита требует второго, недоступного агентам источника полномочий: отдельной учётной записи независимого ревьюера с обязательным одобрением или подписи владельца отдельным ключом, закрытая часть которого не передаётся ИИ и подключённым инструментам. До настройки такого контроля нельзя заявлять, что изменения Agent OS защищены от любого обхода.

Публичная GitHub-документация отдельно предупреждает о неоднозначных одноимённых статусах Actions. По возможности организационные rulesets должны требовать **конкретный доверенный workflow**, а не только совпадающее название job. Обычная веточная защита `required status check` с `GitHub Actions` как источником — промежуточный уровень, не равноценный независимому сервису проверки.
4. Старые открытые PR сохранены по точным HEAD в `transition.legacyHeads` без автоматического заднего пересмотра. Изменение их HEAD после принятия правила потребует нового решения — без безусловного постоянного обхода.
5. Отдельная задача `DONE` не делает демонстрацию готовой. Этап `ACCEPTED` требует реального защищённого run/SHA доказательства и владельческого решения. Фиктивная запись `PASS` или тест не является достаточной приёмкой. Для S4-G1 приёмка должна указывать `acceptanceSha` (ровно 40 символов), точную ссылку на разрешённый одноразовый workflow ремонта, успешный защищённый job и фактическое одобрение среды staging владельцем без admin bypass. Проверка сверяет данные через GitHub API и **отказывает**, если любой факт не подтверждён. Проверки приёмки остальных этапов требуют отдельного утверждения их путей и заданий — произвольная успешная ссылка не разблокирует следующий этап.

## GitHub enforcement: два уровня

- Существующий job `validate` сохраняет имя/status context. Сначала на одноразовом GitHub-hosted runner выполняются установка зависимостей, offline governance regressions, lint, typecheck, существующие focused tests, build и локальный artifact smoke. Отсутствие допуска на область PR не мешает этим проверкам; собственная ошибка проверки по-прежнему может остановить последующие обычные шаги.
- В конце **того же** `validate` выполняется `check-demo-release.mjs --ci` с `if: ${{ !cancelled() }}` и тайм-аутом 5 минут. Он запускается и после ошибки исходных проверок; ошибка любого шага сохраняет FAILURE. Отмена/тайм-аут не являются SUCCESS. Без точного допуска out-of-stage PR остаётся FAILURE; изменение управляющих файлов требует CONTRACT-CHANGE. Новое HEAD отменяет старый допуск к выпуску, но не возможность запустить source checks.
- Negative tests работают до prune devDependencies; завершающий checker использует только Node builtins. Checkout обоих source jobs имеет `persist-credentials: false`, deployment secrets и protected environments отсутствуют, read-only GITHUB_TOKEN явно передаётся только завершающему шагу допуска. Это ограничение передачи, **не** изоляция токена от произвольного кода внутри того же runner: `validate` исполняет PR source и не заменяет независимую границу доверия.
- Артефакт, созданный до завершающего gate, является только результатом изолированной проверки, не допуском к deployment. Он не публикуется этим workflow. Потребители обязаны требовать успешный полный run и независимый gate для точного SHA, не только зелёный Build.
- Семантика условия соответствует [GitHub status check functions](https://docs.github.com/en/actions/reference/workflows-and-actions/expressions#status-check-functions). Offline scheduling tests — модель условий плюс настоящий checker с подставленным API, не доказательство физического запуска GitHub.
- Отдельный `.github/workflows/asi-release-governance.yml` работает на `pull_request_target` и **никогда не исполняет код проверяемого PR**: загружает скрипт из защищённой base main, получает SHA проверяемого PR как git-данные и проверяет область изменений. В GitHub этот job называется `release_governance`.

**ВАЖНО:** публикация workflow и даже его merge не делают второй check обязательным. Для настоящего fail-closed контроля владелец после независимого review отдельно разрешает GitHub branch-protection/ruleset изменение: добавить `release_governance` в required checks для `main` вместе с существующим `validate`; запретить bypass и исключения администратора. До этого нельзя заявлять, что защиту невозможно обойти. Ни этот документ, ни API-комментарий не разрешают merge, protected runs, SSH, SQL, изменения сервера, Vercel/production, Sentinel или бронирования.

## Конечная точка

Текущие этапы идут по порядку `S4-G1` → `S4-G6`. После отдельной физической приёмки последнего этапа владелец фиксирует `READY_FOR_DEMO`. Добавление не требовавшихся функций переводится в следующий релиз, а не задерживает показ. Изменение финишной точки само является защищённым решением владельца.

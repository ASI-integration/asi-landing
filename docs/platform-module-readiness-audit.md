# Честный аудит готовности модулей платформы

Оценка по состоянию репозитория на момент аудита (структура `src/lib/*`, маршруты `src/app/*`, скрипты `scripts/*`). Проценты — **честная субъективная оценка** по framework из `docs/platform-90-percent-readiness-framework.md`, с раздельными слоями.

---

## 1. Location / Residential

### Demo layer

| Аспект | Состояние |
|--------|-----------|
| Текущее | Страницы демо/анализа, `src/lib/report/generator.ts` — **детерминированный** отчёт от строки адреса без БД; визуально полный отчёт. |
| Сильное | Быстрый цикл «адрес → экран»; предсказуемость для маркетинга. |
| Сырое | Демо **не обязано** отражать реальный OSM/рынок; риск восприятия как «реальные цифры». |
| MVP-only | Синтетические конкуренты/ADR/occupancy из хеша адреса. |
| Sellable | Как «иллюстрация методологии» — да; как финансовый совет — нет без дисклеймера. |
| Production-like | Низкая как источник решений о доходе; высокая как **лендинг-демо**. |
| **%** | **~70%** (как демо-продукт), **~35%** (как decision-grade revenue layer). |

### Standalone / sellable layer

| Аспект | Состояние |
|--------|-----------|
| Текущее | `standalone-report.ts`, paywall-типы, API `location-standalone-report`, хранение отчётов (`standalone-report-store`). |
| Сильное | Версионированные секции отчёта; связка с реальным пайплайном анализа (частично). |
| Сырое | Зависимость от качества геокодинга/OSM; нужна жёсткая маркировка proxy vs measured. |
| MVP-only | Упрощённые доходности/стратегии без внешнего рыночного слоя. |
| Sellable | Pilot: «локационный разбор по OSM + эвристики» — да при честном scope. |
| Production-like | Средне: нужен контроль качества и географический control set. |
| **%** | **~55–60%**. |

### Core engine layer

| Аспект | Состояние |
|--------|-----------|
| Текущее | `gravity-scoring.ts`, `location-score.ts`, `overpass.ts`, `audience-scoring.ts`, `neighborhood-environment.ts`, `foot-traffic.ts`, `explanation.ts` — **зрелый** набор чистых функций + конфиг. |
| Сильное | Модульность, переиспользуемые объяснения, конфиг весов. |
| Сырое | Зависимость от полноты OSM; нет полноценного «spatial barrier / micro-catchment» как в commercial roadmap. |
| MVP-only | Foot traffic и часть модификаторов — прокси-слои. |
| Sellable | Как библиотека скоринга — близко к пилоту. |
| Production-like | Высокая **относительно других модулей**; упирается в **data ceiling** OSM/геокодера. |
| **%** | **~65–72%**. |

## 2. Location / Commercial-Retail

### Demo layer

| Аспект | Состояние |
|--------|-----------|
| Текущее | UI/страницы под коммерческий сценарий в разработке (`CommercialReportView`, RU pages в git). |
| Сильное | Визуализация формата и нарратива. |
| Сырое | Риск показать «карту» без геометрии коридоров/барьеров = **вводящая в заблуждение** точность. |
| MVP-only | Вердикты format-fit без полной пространственной модели. |
| **%** | **~50–58%**. |

### Standalone / sellable layer

| Аспект | Состояние |
|--------|-----------|
| Текущее | `LocationCommercialReport` v2 в `standalone-report.ts`, `commercial-format-fit.ts`, коммерческий модификатор окружения. |
| Сильное | Явный вердикт по форматам, структурированные entry/explanation RU. |
| Сырое | Sellable обещания про «коридор / микро-катчмент / барьеры» **ещё не закрыты** кодом как decision-grade. |
| **%** | **~48–55%**. |

### Core engine layer

| Аспект | Состояние |
|--------|-----------|
| Текущее | Тот же gravity core + commercial format fit + модификаторы; **нет** отдельного слоя micro-catchment / corridor graph / barrier-aware routing в `gravity-scoring` (на момент аудита — изометрическая/радиальная логика). |
| Сильное | Итерации tuning (доки в `docs/commercial-*`, скрипты валидации в `scripts/`). |
| Сырое | **Главный технический gap** для commercial: пространственная достоверность. |
| **%** | **~45–52%** (ниже residential из-за более жёстких требований к геометрии и footfall proxy). |

## 3. Communication

### Demo layer

| Аспект | Состояние |
|--------|-----------|
| Текущее | Маркетинговые сценарии в i18n, «как это выглядит». |
| **%** | **~80%** (достаточно для сайта). |

### Standalone / sellable layer

| Аспект | Состояние |
|--------|-----------|
| Текущее | Каналы (Telegram и др.), `orchestrator.ts`, шаблоны, сессии, persistence, dashboard страницы. |
| Сильное | Большой объём тестов в `src/lib/communication/__tests__/*`; идемпотентность, аудит, handoff. |
| Сырое | Зависимость от качества внешних резерваций/Supabase; `knowledge.ts` содержит **legacy/mock** fallback — нужна дисциплина окружений. |
| MVP-only | Часть эвристик intent без LLM. |
| Sellable | Pilot-ready для операторов с human-in-the-loop. |
| **%** | **~68–74%**. |

### Core engine layer

| Аспект | Состояние |
|--------|-----------|
| Текущее | `decision-engine.ts` (autonomous routing), `action.ts`, `escalation-engine.ts`, связка с ops (`tasks`, `checkin-gate`). |
| Сильное | Явные политики эскалации, safety для платежей и срочных кейсов. |
| Сырое | Полный матричный coverage всех OTA edge cases — нет; мультиязычные nuance. |
| **%** | **~70–76%**. |

## 4. Pricing / Revenue

### Demo layer

| Аспект | Состояние |
|--------|-----------|
| Текущее | Числа в демо-отчёте локации (`generator.ts`) — **синтетика**. |
| **%** | **~40%** (намеренно прокси). |

### Standalone / sellable layer

| Аспект | Состояние |
|--------|-----------|
| Текущее | Нет выделенного модуля «динамическое ценообразование»; ценообразование размазано по демо и коммуникации (сценарий `pricing`). |
| **%** | **~25–35%**. |

### Core engine layer

| Аспект | Состояние |
|--------|-----------|
| Текущее | Нет отдельного revenue optimization engine; зависимость от внешних рыночных данных не закрыта. |
| **%** | **~20–30%** без внешнего data layer (см. summary). |

## 5. Ops / Autonomy

### Demo layer

| Аспект | Состояние |
|--------|-----------|
| Текущее | Меньше визуального «демо-продукта», больше интеграции в comm pipeline. |
| **%** | **~45%**. |

### Standalone / sellable layer

| Аспект | Состояние |
|--------|-----------|
| Текущее | `ops/tasks.ts`, инциденты `incident-service.ts`, UI dashboard частично через коммуникацию. |
| Сильное | Связь orchestrator → `createOpsTask`, `evaluateCheckinReadiness`. |
| Сырое | Нет полного «autonomous ops product» как отдельной линейки. |
| **%** | **~50–58%**. |

### Core engine layer

| Аспект | Состояние |
|--------|-----------|
| Текущее | `ops/decision-engine.ts` — правила по инцидентам, тесты `stay-flow-runner`, `checkin-gate`. |
| Сильное | Явные типы решений, payer recommendation, режимы коммуникации. |
| Сырое | Нужны live datasets инцидентов и калибровка порогов под реальных операторов. |
| **%** | **~58–65%**. |

## 7. Cross-module decision engine / orchestration

### Demo layer

| Аспект | Состояние |
|--------|-----------|
| Текущее | Маркетинговые обещания «платформа» без единого UI всех модулей. |
| **%** | **~40%**. |

### Standalone / sellable layer

| Аспект | Состояние |
|--------|-----------|
| Текущее | Фактическая оркестрация сосредоточена в **`communication/orchestrator.ts`** (связка identity, LLM, payments, ops). |
| Сырое | Нет единой **платформенной** шины решений (location + pricing + finance + ops) с одним контрактом. |
| **%** | **~35–45%**. |

### Core engine layer

| Аспект | Состояние |
|--------|-----------|
| Текущее | Два «decision-engine»: comm (`communication/decision-engine.ts`) и ops (`ops/decision-engine.ts`) — **не унифицированы**. |
| **%** | **~38–48%**. |
